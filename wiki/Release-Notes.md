Every release note lists the database migrations it adds (TR-OPS-01) and the "should" requirements it meets ([[Technical Requirements]]).

## 0.3.0 (not yet released)

What `main` holds for the next release. It is still a 0.x release, so it makes no compatibility promise.

- **Overdue time on task items (#472, PD-111).** Items of `GET /tasks` now carry `slaState` (`NONE`, `ON_TIME`, `DUE_SOON`, `BREACHED`) and `overdueBy`, an ISO 8601 duration in whole minutes since `dueAt`, null unless breached, both computed by the engine at query time. New setting `horus.bpm.processes.query.due-soon-window` (`PT1H`). Additive; no migration.
- **Tenant display names in `/me` (#474).** `GET /api/bpm/me` adds `tenant.names`, a display name for each tenant the caller may switch to and for no other, from `horus.bpm.display-names.tenants.<id>.<language>` or the new default method `DisplayNames.tenant(tenantId, locale)`. Additive; hosts that set nothing see no change; no migration.
- **FEEL in conditions and scripts (#498).** A sequence-flow condition and a script task may be written in FEEL, under the DMN FEEL URI (`amount > 1000 and tier = "gold"`), beside `urn:horus-bpm:expr:v1`, which is unchanged. Null, number and money rules are the same; a FEEL text hashes in the v1 normal form, so one meaning is one `definitionHash`; any other language is still refused by name. No migration.
- **FEEL on conditional events (#492, #498).** The condition of a conditional start or catch event may be written in FEEL as well; it is checked at import, hashes in the v1 normal form and exports back with its language. No migration.
- **Script budget through the expression API (#517).** New `ExpressionLanguages.withBudget(language, stepBudget, timeoutMillis)` in `bpm-expression`; the Process Engine core no longer reaches the expression internals, and the architecture rule says so without an exemption.
- **Embedded sub-process (#486).** A BPMN `subProcess` runs from its own start to its own end in its own scope: the parent continues after the inner end, a parallel join inside waits only for its own branches, a cancel cancels everything inside, and a failure with `onFailure: compensate` undoes only the sub-process's own steps. It reads and writes the process variables. An event sub-process is still refused (`S1`). The cockpit draws it closed with a count or open in place and nests its steps in the timeline, read only. No migration.
- **Boundary events (#489).** A timer, error or escalation boundary on a task, call activity or sub-process, interrupting or not (`cancelActivity="false"`). An interrupting one cancels the step, its work item or its called child and takes its own flow; an error boundary takes a handler's business error by its code before it becomes an incident, and a failed child as `CHILD_FAILED`.
- A boundary timer is one ordinary timer job, cancelled when the step ends on its own. The cockpit draws the boundary on its step and the timeline names the boundary that fired. No migration; see [[Process Engine Importing BPMN|Process-Engine-Importing-BPMN]].
- **Error, escalation, terminate and link events (#493).** Error and escalation end events and the escalation throw event, caught by those boundaries; an error nothing catches opens an incident on the end event and an escalation nothing catches is recorded while the flow goes on.
- A terminate end ends every other token of its scope (the instance at the top level, the sub-process inside one); a link throw jumps to the catch of its name in the same scope and a throw with no catch is refused at import with its element id. Worked example: `card-dispute.bpmn`.
- **Signal and conditional events (#492).** Signal start, intermediate catch, intermediate throw and end events, and conditional start and intermediate catch events, import and run. A signal is broadcast within one tenant only, by a throw or by the new `POST /signals` (`processes:signal:broadcast`, `Idempotency-Key` required, answers `202`); the waiters continue through wake-up jobs, once each, and the timeline shows how many a throw woke. A conditional catch passes at once when true, otherwise it is asked again when the instance's variables change. New codes `SIGNAL_REF_INVALID`, `SIGNAL_NAME_INVALID`, `CONDITION_INVALID` (import) and the step failure reason `START_CONDITION_FALSE`. The cockpit draws the symbols and the timeline entries, read only. **Migration:** Process Engine `V46__pre_signal`, two new tables and the job kind `SIGNAL_DELIVERY` (rollback in the file).
- **Messages and correlation (#491).** Message start, intermediate catch and throw, message end, receive task and send task are imported and run. `POST /messages:correlate` (`processes:message:correlate`, `Idempotency-Key` required) delivers a message to the one instance waiting for its name and `horus:correlationKey`, or starts the process with a message start event; a message with no waiting instance is `422 MESSAGE_NOT_CORRELATED` and is not kept, two matches are `409 MESSAGE_CORRELATION_AMBIGUOUS`. A sent message goes to the host's new `MessageAdapter` port, once per step. The cockpit shows the steps in the diagram and the timeline. **Migration:** Process Engine `V47__pre_message_subscription` (new table; rollback: drop it when no instance waits for a message).
- **Loops and multi-instance (#496).** A task, a call activity or an embedded sub-process can run once per item of a list, in parallel or one after another, or repeat as a standard loop (`loopMaximum` and a condition). Each repetition has a `loopCounter` and an element variable; `nrOfInstances`, `nrOfActiveInstances` and `nrOfCompletedInstances` feed a `completionCondition`, which cancels the repetitions still running; the output list is in item order. New setting `horus.bpm.processes.multi-instance.max` (1,000) bounds the repetitions of one step: over it, an incident opens and no task is created. Activity entries gain `instances` counters. The cockpit marks the step on the diagram and shows "3 of 5 done", read only. No migration.
- **Transaction, cancel and full compensation (#488).** The `saga` block is exported as the standard `transaction`; a compensation boundary event with a compensation activity (`isForCompensation`) is an undo like `horus:compensate`; a compensation throw or end event undoes its scope or one activity and the flow goes on; a cancel end event in a transaction compensates it and leaves through its cancel boundary event.
- A compensation of an enclosing scope now also undoes the sub-processes completed in it, each step once, newest first across scopes; the cockpit draws the new elements and lists the undos newest first. New migration Process Engine `V48__pre_compensation_instance_order` (one new column on `pre_compensation_stack`); see [[Process Engine Importing BPMN|Process-Engine-Importing-BPMN]].
- **Plain, manual and script tasks (#485).** `task` and `manualTask` pass the token on; `scriptTask` runs one expression (1,000 characters, 500 steps, no host code) into `horus:resultVariable`; FEEL scripts follow.
- The cockpit draws the three and shows the result variable in the timeline. No migration.
- **Step catalogue (#103, PE-F-52).** `GET /api/bpm/processes/v1/step-catalogue` lists what the host registered and nothing else, for the modeller: service handlers (local and remote, with input schema and `compensable`), agent adapters, the rule sets with a version in effect (and those that meet the guardrail contract), the tenant's calendars and the roles the host lists. Needs `processes:author`; the tenant comes from the signed-in context; the `ETag` is a hash of the body. New default methods `ServiceTaskHandler.inputSchema()` and `compensable()`, the same on `ServiceAdapter`, `AgentAdapter.inputSchema()` and `RoleCatalogue.roles(tenant)`, so no existing host changes; the embedded Rule Engine entry point gains the default method `TenantScopedRuleEngine.publishedRuleSets`. No migration.
- **Task list role fan-out cap (#408).** `GET /tasks` reads one queue per role and group of the caller. A caller whose roles and groups together exceed the new setting `horus.bpm.processes.query.max-roles` (100 by default, at most 1,000) and who names no `role` or `group` now gets `400 ROLE_FAN_OUT_EXCEEDED` with `cap` and `provided`, instead of an unbounded read. **Behaviour change:** a user with more than 100 roles and groups sees the error until the host raises the cap, trims the role list or the client sends `role` or `group`. No migration.
- **Localised field titles in the review (#386).** An agent step may declare `<horus:fieldTitles>` with English and Vietnamese (or any language) titles per input and output field; the review task returns them as `review.fieldTitles`, so the cockpit shows `Điểm rủi ro` instead of `riskScore`. A malformed set is refused at import with `FIELD_TITLES_INVALID`. The titles are part of the definition, so adding them to a step changes its definition hash. No migration.
- **Tenant switch isolation at the engine (#85).** The Process Engine has its own test that, after a tenant switch, the original tenant's instance, task and cancellation are `404` and nothing is written (`PRE-038`). No change in behaviour.
- **Conditional reads of the task and incident lists (PRE-218).** `GET /tasks` and `GET /incidents` return an `ETag`, a hash of the body, and answer a matching `If-None-Match` with `304` and no body. The tag changes with any item, page or cursor, and with the caller's own view (`allowedActions`); it is computed after the tenant and permission checks from what the caller may see, so it never matches another tenant's list. No migration.
- **Tenant switches in the audit trail (#451).** Every accepted tenant switch is handed to the new `TenantSwitchAudit` SPI of `bpm-host-metadata` with the actor, the original and the new tenant, the time and the correlation id, before the call reaches engine data. The default writes it as one `tenant.switch.accepted` line on the new `io.github.dhluong90.bpm.audit` logger (keep it at `INFO`); a host bean, for example one that appends to its own audit table, replaces it, and a sink that throws fails the call. The security log line stays. A refused switch writes no audit record. Outside `dev`, with an audience configured, every `JwtDecoder` bean the host defines itself is named in one start-up WARN (`jwt.decoder.audience.unchecked`): the starter applies `security.audiences` only to Spring Boot's own decoder. No migration.
- **Warnings about unclassified fields (#438, PD-146).** Masking stays opt-in; the engines now remind authors of fields they did not classify, and never block. Rule Engine: every input that declares neither `mask: true` nor `mask: false` is listed as `UNCLASSIFIED_INPUT` in the version's `warnings` (import, publication request, review) and in the new `warnings` of `:validate`; it never needs an acknowledgement. Process Engine: `GET .../versions/{v}` and `:request-approval` carry `warnings` with one `UNCLASSIFIED_FIELD` per agent step input or output schema property without `mask`. Outside `dev` each engine logs one WARN at start-up counting them per approved version, never a field value. New settings `horus.bpm.rules.classification.warn-unclassified` and `horus.bpm.processes.classification.warn-unclassified` (both `true`). New SPI default method `MaskingPolicy.warnUnclassified(tenant)`. **Migration:** Process Engine `V45__pre_definition_active_index`, a partial index on `pre_definition` built `CONCURRENTLY` outside a transaction (rollback: `DROP INDEX CONCURRENTLY idx_pre_definition_active`).
- **Display names (#442).** New host SPI `DisplayNames` and endpoint `GET /api/bpm/display-names?roles=&groups=&users=` (host contract 1.3.0): readable names in the caller's language, from `horus.bpm.display-names.roles|groups|users.<id>.<language>` by default. `GET /approvals` in both engines adds `requestedByName` (the id when no name is known), through the new default method `CallerResolver.displayNameOf`. **Upgrade note:** a class that implements both engines' `CallerResolver` inherits two `displayNameOf` defaults and no longer compiles until it overrides `displayNameOf` once. `409 ASSIGNEE_NOT_ALLOWED` adds `reason` (`ALREADY_ASSIGNED`, `FOUR_EYES_PARTICIPANT`, `RESERVED_IDENTITY`, `MISSING_ROLE`, `MISSING_GROUP`) and, for a missing role or group, `required`. No migration.
- **Retention check reads a build-time version (#450).** The 1.0 retention requirement now reads the engine version from `rule-engine.properties`, written by the build, instead of the jar manifest, so a shaded or repackaged jar or a class directory can no longer skip it. A version that is missing or cannot be read fails closed: outside `dev`, start-up is refused until `decision-log.retention` is set. **Behaviour change:** on 0.3.0 nothing changes, because the build writes a readable 0.x version; an IDE build whose resources were not filtered by Maven must set the retention or run on `dev`. The embedded-engine grant still compares the jar manifests of the two starters: in a shaded jar it fails closed (no grant), which is safe.
- **Call a child process and wait (#92, PD-127, PD-144).** A BPMN `callActivity` is a `callProcess` step: `calledElement` is the key of a definition of the same tenant, `horus:calledVersion` pins a version, `<horus:input>` passes values to the child and `<horus:output name from>` brings named child variables back; nothing else crosses, and `horus:in="all"` is refused. The parent's token waits as the new status `WAITING_CHILD`; the child's end writes a `CALL_RESULT` job that resumes the parent in its own transaction, so the child never locks the parent. A child that fails or is cancelled opens an incident `CHILD_FAILED` or `CHILD_CANCELLED` (or starts the parent's compensation with `onFailure: compensate`), and a retry starts a new child. Cancelling the parent cancels its children with the reason `parent cancelled`. A completed child is undone only by its call step's `horus:compensate` handler, which a call inside a `saga` must declare (`COMPENSATION_REQUIRED`). New setting `calls.max-depth` (5, lowered only; deeper is the incident `CALL_DEPTH_EXCEEDED`). `callActivity` is no longer refused at import. **Behaviour change:** `GET /instances/{id}` may show a token with status `WAITING_CHILD`; clients that switch on token status need the new value.
- **Migration with renamed and removed steps (#106, TR-MIG-03).** `POST /migrations` takes optional `mappings` (`{from, to}`) and `cancellations` (`{step, moveTo, reason}`). A mapped step keeps its tasks, claims, due times and four-eyes rule; a cancelled step's task or due job is cancelled with the reason and the token continues at `moveTo`, which runs as on arrival; a call in flight is never cut off (`STEP_IN_FLIGHT`, the instance moves on a later plan). The dry run shows `MAPPED` and `CANCELLED` steps and an `impact` count (mapped, cancelled, in flight, unmapped). Instructions that cannot be carried out are `422 MIGRATION_PLAN_INVALID`. Four-eyes for the execution is unchanged; new reserved setting `migration.cancel-approval` (`single`; `four-eyes` is refused at start-up). The cockpit migration screens (#107, #108) use these endpoints and follow.
- **BPMN import writes layout revision 1 (#445).** The diagram of an imported BPMN file becomes layout revision 1 of the new version (source `BPMN`), apart from the definition and without changing its hash; a file without a diagram stores none, and later changes in the cockpit are new revisions that need no approval.
- **Migrations V40 to V44 (Process Engine).** `V40__pre_migration_instructions` (one `NOT NULL` column with a constant default on `pre_migration`), `V41__pre_timer_inflight_index` (a partial index on `pre_timer`, built `CONCURRENTLY` outside a transaction), `V42__pre_call_activity` (the token status `WAITING_CHILD` and the job kind `CALL_RESULT`, both checks added `NOT VALID` then validated; four nullable or constant-default columns on `pre_instance`), `V43__pre_instance_call_indexes` (a unique index and a parent index, both partial and built `CONCURRENTLY`) and `V44__pre_token_live_waiting_child` (the two live-token indexes rebuilt `CONCURRENTLY` with `WAITING_CHILD` in their predicate, under the same names). Forward-only, rollbacks documented in each file. **Upgrade note:** run V42 to V44 before any replica starts a `callProcess` step; a replica of an earlier 0.3.0 snapshot that reads a `WAITING_CHILD` token does not know the status.
- **Process Engine migration order in this release.** Flyway applies `V36__pre_node_stats_retention_index`, then `V40` to `V44`, then `V45__pre_definition_active_index`, `V46__pre_signal` and `V47__pre_message_subscription`, in that numeric order. Versions 37 to 39 are not used, and nothing later may take them. The example host's `pre_schema_history` check lists the same order.
- **Standalone cockpit on another origin (#11) and opt-in tenant switching (#85).** New host-wide settings under `horus.bpm.`, shared by both engines: `rest.cors.allowed-origins` (exact origins, empty by default, so CORS stays off; no wildcard, no credentials mode; `rest.cors.allowed-headers`, `allowed-methods`, `exposed-headers` and `max-age` have defaults), `security.audiences` (a bearer token whose `aud` names none of them is `401`) and `tenancy.switching.enabled` (default `false`) with `tenancy.allowed-tenants-claim` (default `allowed_tenants`). **Behaviour change:** none for existing hosts, since every setting is off unless set. With switching on, `X-Tenant-Id` is accepted only for the signed-in tenant or a tenant in the verified token's allowed claim; anything else is `403 TENANT_NOT_ALLOWED`; each accepted switch writes `tenant.switch.accepted` on the security log, and `/api/bpm/me` lists the allowed tenants and `/api/bpm/meta` reports `tenancy.switching`. Outside the `dev` profile the host refuses to start with a CORS origin and no audience. New optional dependency of `bpm-host-metadata`: `spring-security-oauth2-jose`. No migration. See [[Rule Engine Configuration]].
- **Breaking change of a 0.x release: both engines list the elements they refuse as `unsupportedElements` with one item shape (#380, PD-141).** `DMN_UNSUPPORTED_ELEMENT` and `EXPRESSION_LANGUAGE_UNSUPPORTED` (Rule Engine) no longer carry `elements`; `BPMN_UNSUPPORTED_ELEMENT` (Process Engine) no longer carries `problems`. Both carry `unsupportedElements`, in document order, up to 100 (`violationsTruncated` keeps its name), each item `{ element, elementId, line, stage, message }`: the Rule Engine's `id` is now `elementId`, the Process Engine's item has no `code`, and `message` is new in the Rule Engine. `problems` stays for `VALIDATION_FAILED` and `GUARDRAIL_CONTRACT_INVALID`. **Change** a client that reads `elements` or `problems` on these three codes to read `unsupportedElements`, and read `elementId` for the id. Java: `DefinitionVersion` gains a `warnings` component (the earlier constructor is kept) and `UnsupportedElement` gains `message()`. See [[Common Error Codes|Common-Error-Codes]].
- **Warnings on a successful BPMN import (#380).** A `201` answer to `POST /definitions` lists vendor attributes and extension elements that were kept in the stored source and not read, in `warnings` as `FOREIGN_EXTENSION_IGNORED` (additive; absent when there are none, and absent when the version is read later). The stage of an intermediate throw event comes from its event definition: a signal or message throw is `S2`, an escalation throw `S1`.
- **Spreadsheet round trip in the Rule Engine (#39, engine side).** `GET .../versions/{v}/export?format=csv` writes a version as a UTF-8 CSV file that Excel opens, and `POST .../versions?base={v}` with `Content-Type: text/csv` imports an edited file as the next draft, with cells such as `GOLD, PLATINUM`, `>= 50000000 VND`, `18 to 65`. The file must keep the base version's inputs and outputs; the rows go through the checks of an imported document; a damaged cell (`5E+07`, `50,000,000`, a date that is not an ISO date, an amount with no currency) is refused with its rule and column and is never read as another value; no error quotes a cell. New problem codes `CSV_*` (in every language of the message catalogue), new `SourceFormat.CSV` (add-only enum value) and `VersionService.importCsv`. No migration. The cockpit screen follows in #39.
- **Rule set templates (engine side of #83).** `GET /rule-set-templates` (`rules:author`) lists four built-in starting points (fee by tier, eligibility with reason codes, limit by segment, blank) and any `.json` files the host adds in `horus.bpm.rules.templates.location`; `horus.bpm.rules.templates.hidden` hides a built-in one.
  Every template is checked at start-up like an imported document, and an invalid file stops the start and names itself. Feature flag `rules.templates`. See [[Rule Engine Authoring Decision Tables]].
- **Simulation reports for approvers (engine side of #109).** `POST` and `GET /rule-sets/{name}/versions/{v}/simulation-reports[/{id}]` store one immutable report bound to the version's `canonicalHash`, with counts and up to 50 changed rows and no input or masked value; it reads `OUT_OF_DATE` once the draft changes.
  `:request-publish` takes an optional `simulationReportId` (`404 SIMULATION_REPORT_NOT_FOUND`, `409 SIMULATION_REPORT_OUT_OF_DATE`); the setting `lifecycle.require-simulation-report` lists rule sets that must carry one (`409 SIMULATION_REPORT_REQUIRED`) and shows in `/api/bpm/meta`. Feature flag `rules.simulation-reports`. See [[Rule Engine Simulation and Testing]].
- **Replay readings (engine side of #96).** `POST .../versions/{v}:simulate-history-readings` replays logged decisions and reads each one in plain language, the logged outcome and the simulated outcome in the draft.
  A decision with a masked input that had a value, or whose version cannot be evaluated again, is `REPLAY_NOT_POSSIBLE` with the input names and no sentence; at most 500 decisions. Feature flag `rules.history-readings`.
- **Migrations V31 and V32 (Rule Engine).** `V31__rle_simulation_report` (the report table, refusing `UPDATE`, `DELETE` and `TRUNCATE`) and `V32__rle_simulation_report_attachment` (the report a publication request carries). Both are new objects, so a rolling upgrade needs no ordering; rollback is a new forward migration that drops them and loses the stored reports.
- **Rule set display name (engine side of the cockpit lists).** A rule set document may carry `displayName` (1 to 100 characters, part of the version); `GET /rule-sets` and `GET /rule-sets/{name}` return `displayName`, or the key made readable (`card-fee` reads `Card fee`) when the document names none.
  No migration: the name is read from the latest version's stored document.
- **Migrations:** Rule Engine `V18__rle_version_retire_request` (the pending four-eyes retirement on `rle_version`: who asked, when, the reason and the confirmation), `V19__rle_decision_log_drop` (the append-only `rle_decision_log_drop` table, one row per tenant and one total row for each decision log month that retention drops) and `V20__rle_decision_correlation_index` (the case-reference index on `rle_decision`, led by tenant and correlation id). Process Engine `V13__pre_incident` (the new `pre_incident` table and three partial indexes on it; additive, nothing existing is touched).
- **Pending approvals list (#31).** `GET /approvals` in both engines lists the versions waiting for a second person, oldest request first, for the cockpit approvals queue: the key and version, `requestedBy` and `requestedAt`, the `canonicalHash` or `definitionHash` to name when approving, `lockVersion`, and the caller's `allowedActions` with a reason code for each action that is denied. Needs read permission only. Rule Engine `V30__rle_version_pending_index` (a Java migration) and Process Engine `V35__pre_definition_pending_page_index` build one partial index each `CONCURRENTLY`, outside a transaction; a replica of the previous release is unaffected.
- **Upgrade note: Rule Engine V20 is a Java migration that does not block writes, and migrations need a direct database connection.** V20 runs outside a transaction: it creates the parent index `ON ONLY rle_decision`, then builds the index on each existing partition with `CREATE INDEX CONCURRENTLY` and attaches it, so evaluations keep writing decisions while it runs. Partitions created later get the index automatically. A rerun is a no-op, and a build left invalid by an interrupted run is dropped and rebuilt. The Rule Engine migrator now takes Flyway's migration lock as a session advisory lock, as the Process Engine does, so run migrations on a direct connection, not through PgBouncer or another pooler in transaction mode. The running engine still works behind a pooler in transaction mode.
- **Agent SPI additions.** `AdapterResult.Completed.labels()` carries string labels about how an answer was produced, with the reserved keys `model`, `promptVersion`, `usage.inputTokens` and `usage.outputTokens` (constants on `Completed`) plus the host's own keys; `AdapterResult.completed(output, labels)` builds one. Labels are kept unchanged in the agent history, bounded by `agents.labels.max-count` (16), and the engine takes no decision from them; an answer over the bounds fails the attempt with `AGENT_LABELS_INVALID`. `AgentInvocation.outputSchema()` gives the adapter the step's output schema without the engine's `mask` annotations. The new `InputMasker` SPI turns a masked step input into its stored fingerprint (`hmac:<keyId>:<hex>` under the tenant's masking key, `***` without one). The test-support module adds the `AgentInvocations` and `AdapterCalls` builders, which keep compiling when a component is added to those records. See [[Guarded Agent Steps|Guarded-Agent-Steps]].
- **Behaviour change: a job that fails for good opens an incident.** When an asynchronous job fails for good (retries used up, a business error, an agent answer refused with `onViolation: fail`, or a job claimed too often), the engine opens one `OPEN` row in `pre_incident` in the same transaction, records `INCIDENT_RAISED` in history and emits `processes.incident.raised.v1`. The token stays on the step in `WAITING_ASYNC`. The incident carries its own code (`AGENT_TIMEOUT`, `AGENT_SCHEMA_INVALID`, `UNHANDLED_BUSINESS_ERROR`, `MAX_ATTEMPTS_REACHED`), the number of retries and a cause built from codes only. `IncidentService.openIncidents(instanceId)` reads them in the caller's tenant.
- **Discard a draft (#418).** `POST /rule-sets/{name}/versions/{v}:discard` (`Idempotency-Key` and `If-Match` required, `rules:author`, only the draft's author) moves a `DRAFT` to the new terminal status `DISCARDED`. Nothing is deleted: the version, its rules and hashes stay, one `DISCARDED` row is added to the history (actor and optional reason), and one `rules.version.discarded.v1` event is written. The version is left out of `GET .../versions` and its number is never used again; a published or retired version cannot be discarded (`409 INVALID_STATE`). `allowedActions` of a draft holds `discard` for its author. New status `DISCARDED` and history action `DISCARDED` are additive enum values in the API and the Java `VersionStatus` and `LifecycleAction`; a client that switches over the status must handle them. Migration `V28__rle_version_discarded` widens three CHECK lists (no column, no row change). **Upgrade note: finish a rolling upgrade before anyone discards a draft;** a replica on the earlier release cannot read a `DISCARDED` row.
- **Helpful syntax errors (#419).** A `SYNTAX_ERROR` problem from `:validate` now also carries `expected` (the token or form the parser expected at `position`, in every language of the message catalogue, `en` and `vi` ship) and `example` (a short correct expression). They come from the catalogue by the kind of error, never from the cell, so a masked value is not echoed. Both members are additive and absent on other codes.
- **Upgrade note (PD-130): decision log retention is off unless set.** With `horus.bpm.rules.decision-log.retention` unset, every decision is kept, nothing is dropped, start-up is not stopped, and a WARN is logged at every start-up. Set it to `keep-forever` to keep everything without the warning, or to whole months of at least 12, such as `P12M`; a shorter period, a period in days or an unknown value stops start-up naming the property. **From 1.0 the setting is required (#373):** unset then stops start-up, naming the property, on every profile except `dev` on its own (optionally with `test`); the WARN says so.

### Business errors, late results and agent memory

**Behaviour change:** a local handler's business error no longer fails the call with `STEP_FAILED`. The call succeeds, the step waits, and an incident `UNHANDLED_BUSINESS_ERROR` opens with the business code (#55). An agent or remote step's business error fails its job on the first attempt.

A result that arrives after its attempt timed out, after another attempt took over, after the step completed or after the job failed is discarded, writes nothing and never reopens the step.

An agent step can declare `<horus:memory>` to receive declared fields of earlier agent steps' results in the same instance (#101). Process Engine migration `V14__pre_step_result` adds one table. New settings: `agents.memory.max-entries` (16) and `agents.memory.max-bytes` (16384). `AgentInvocation` gains the `memory()` component.

### Breaking change for API clients: an approval binds to the content reviewed

`:approve` and `:reject` now require `expectedCanonicalHash`, the `canonicalHash` of the content the reviewer saw (#275, `RLE-084`, PD-139). A request without it is `400 CONTENT_HASH_REQUIRED`. A hash that no longer matches is `409 CONTENT_CHANGED` (it was `VERSION_CONFLICT` in a pre-release build), carrying `currentCanonicalHash` and `currentLockVersion`, so a client that refreshes and retries on `VERSION_CONFLICT` cannot re-bind a decision to content nobody reviewed. New setting `horus.bpm.rules.approval.require-content-hash` (default `true`); `false` is accepted on the `dev` profile only. The cockpit sends the hash of the content the reviewer opened. **Upgrade note:** a client that approves or rejects through the API must send the hash; a client that sends none is refused until it does.

### Task lists and due times on working hours

`GET /tasks` lists a caller's tasks by assignment (`mine`, `candidate`, `any`), status, role, group, due date and missed deadline, at most 200 to a page, each range read through its own index (#70); a page carries a signed `nextCursor`, valid only for the same tenant and filters, and `limit` above 200 is `400 QUERY_INVALID`. A user task with `horus:sla` and `horus:calendar` is due after that much working time in the tenant's calendar, set once at creation and never moved by a later calendar change; tasks and list items carry `dueAt` (#72). Calendars change through `CalendarService` under four eyes: the proposer cannot approve (`SELF_APPROVAL_FORBIDDEN`), and an approval emits `processes.calendar.changed.v1` naming both people. A task whose calendar the tenant does not have fails its step (`CALENDAR_NOT_FOUND`) and nothing is written; `horus.bpm.processes.calendar.approval: single` is accepted in the `dev` profile only. New permission in the default mapping: `processes:calendar:manage`, and `processes:task:manage` for `assignment=any`. Process Engine migrations: `V20__pre_calendar` (three new tables), `V21__pre_task_due_at` (a nullable column), `V22__pre_task_query_indexes` (five partial indexes on `pre_task`, built `CONCURRENTLY`, and V1's `idx_pre_task_role` dropped `CONCURRENTLY`). On a host with many tasks, run V22 from one replica first: other replicas wait for the Flyway lock while the indexes build.

### Migration plans and the graph diff

A plan names the version a definition's running instances are on and the version they would move to (#74). `POST /migrations` creates one (`Idempotency-Key`, `processes:migration:manage`) and moves nothing; `GET /migrations/{id}` reads it; `POST /migrations/{id}:validate` is a dry run that lists the instances that would move and the steps the target does not have (`STEP_NOT_IN_TARGET`, `STEP_TYPE_CHANGED`, `TARGET_NOT_ACTIVE`) and writes no row. A plan records the four-eyes approval its execution will need; `horus.bpm.processes.migration.approval: single` is accepted in the `dev` profile only, and start-up is refused otherwise (PD-114, PD-131). Executing a plan is not in this release. New settings `migration.dry-run-sample-size` (100, at most 500) and `migration.dry-run-validity` (`PT1H`, at most one hour), which may be lowered only. Event `processes.migration.planned.v1`.

`GET /definitions/{key}/versions/{version}/diff?base={v}` lists the steps and links added, removed and changed between two versions (#76). The same pair always gives the same diff whatever the element order or layout, and swapping them gives the mirror image. At most 1,000 changed values are listed, with `truncated: true` beyond. The diff names steps by BPMN id, name and type and returns no XML and no positions.

### Migration execution and stored diagram layout

`POST /migrations/{id}:execute` proposes moving the running instances of a plan, with a reason (#90). The engine runs the dry run itself; a second holder of `processes:migration:manage`, never the proposer, approves with `:approve` (or rejects with `:reject`), and only the approval lets the runner move instances, in batches of `migration.batch-size`. The runner holds a plan under a lease, so one replica works on it at a time, and a crashed replica's plan is taken over when the lease ends and continues after the last moved instance. One failing instance gets an incident and an outcome `FAILED` and the rest go on. `GET /migrations/{id}/execution` shows exact progress and `GET /migrations/{id}/instances` what happened to each instance. New settings `migration.batch-size` (100, may be lowered only) and `migration.lease` (`PT2M`); new codes `DRY_RUN_REQUIRED`. Process Engine `V34__pre_migration_execution` (one new table, nullable and defaulted columns and three checks on the small `pre_migration` table; no index on a hot table).

`GET` and `PUT /definitions/{key}/versions/{version}/layout` store the position of boxes on a diagram apart from the definition (#102). A save appends a revision, needs `processes:author` and no approval, and never changes the definition, its hash or its status, so tidying a diagram needs no new approval. Revisions are append-only with author and time; `GET .../layout/revisions` lists them. New codes `LAYOUT_INVALID` and `LAYOUT_NOT_FOUND`. Process Engine `V33__pre_definition_layout` (one new table; the table refuses updates and deletes).

### Metrics, events and hourly figures per step

With Micrometer on the classpath the Process Engine registers `horus.pre.instances.started`, `.completed` and `.failed`, `horus.pre.incidents.raised{errorCode}`, the gauges `horus.pre.instances.active` and `horus.pre.incidents.open`, `horus.pre.timer.lag`, `horus.pre.step.duration{stepKind,outcome}`, `horus.pre.async.attempts{kind,outcome}` and `horus.pre.jobs.due.oldest.age{kind}` (#86). Counters move only after the transaction commits. Tags take only engine values (step kinds, outcomes, job kinds and engine error codes; a host business code counts as `UNHANDLED_BUSINESS_ERROR`) and never a tenant, business key, instance id or variable. `definitionKey` is a tag only with `metrics.definition-key-tag: true` (default `false`). Gauges are read by one bounded query every `metrics.gauge-refresh` (`PT30S`), never per scrape. A host without Micrometer starts unchanged.

Every state change hands one event in the standard envelope to the host's publisher inside its transaction. New event types: `processes.step.completed.v1`, `processes.instance.failed.v1`, `processes.calendar.changed.v1` and `processes.migration.planned.v1`. The JSON Schemas of the instance, step, task, incident, compensation and definition events ship in `process-engine/api/events/`, and CI refuses a change to them that is not additive. Payloads carry ids, keys, versions and codes, never a variable or a masked value. CI publishes a throughput report on `main` against 1,000 transitions per second; it warns and never fails the build.

An hourly rollup keeps counts and median and 95th percentile durations per step (#110), read with `GET /definitions/{key}/versions/{version}/node-stats?mode=window&from=&to=` (`processes:read`), which reports `asOf` and the lag. The rollup runs outside every step transaction. One replica takes each slice of history and moves the watermark in the same transaction, so a slice is never counted twice. New settings `stats.rollup-enabled` (`true`), `stats.rollup-interval` and `stats.rollup-lag` (`PT5M`), `stats.rollup-max-slice` (`PT1M`) and `stats.rollup-retention` (`P13M`).

### What-if comparison and Rule Engine list queries

`POST /rule-sets/{name}:compare` with `{ "base", "candidate", "from", "to" }` re-evaluates a past period's logged decisions through two versions in memory and returns outcome counts, output totals per currency in minor units and the 20 most common changes (#120). It needs `rules:simulate` and `rules:log:read` and writes nothing. A decision whose masked input a version reads, or that lacks an input a version reads, is counted under `skipped` (`MASKED_INPUT`, `MISSING_INPUT`) and never guessed. A period holding more decisions than `horus.bpm.rules.simulation.max-history-decisions` (50,000; 1 to 200,000) is `422 HISTORY_TOO_LARGE`; it is never sampled. Java: `RuleEngine.compare(...)`.

Every multi-row read of the Rule Engine store is registered with a declared bound, and CI checks each plan on PostgreSQL 14 and 18, including the partitions a decision log search reads (#368). No query's result changes.

### Decision steps of a process

A business rule task is evaluated as the engine identity `system:process-engine`, on behalf of the user who triggered the step (none after a timer), in the instance's tenant, at the engine clock of the step, with an idempotency key derived from the instance, the step and the attempt. The task worker needs no `rules:evaluate`. A retried step replays the logged decision and writes no second row. The decision log shows the user as `onBehalfOf` (Java `DecisionLogEntry` and `LoggedDecision`, and the REST decision log). Migration `V17__rle_decision_on_behalf_of` adds the nullable column `rle_decision.on_behalf_of`.

### Preview: the Process Engine

The Process Engine is a preview in 0.1.0, for evaluation on the `dev` profile (PD-082, process engine DESIGN section 5.8).

- It imports a first BPMN 2.0 subset: none start and end events, `serviceTask` (a local handler), `businessRuleTask`, `userTask` and `exclusiveGateway`. Every other element is refused by name. See [[Process Engine: import a BPMN file|Process-Engine-Importing-BPMN]].
- Outside `dev`, an imported process stays a `DRAFT`. The approval flow comes later, so nothing in 0.1.0 can activate it there.
- On `dev` only, `horus.bpm.processes.definitions.auto-approve: true` activates imports. Start-up refuses this setting under any other profile.
- Events are handed to your `ProcessEventPublisher` inside the transaction of the state change. They are durable only if your listener writes an outbox row in that transaction.

This is a first subset, not a conformance claim.

### Known limits

- **Cockpit draft editing is off by default.** Turn it on with `authoring.cockpit-drafts: true`. In 0.1.0 each save creates a new draft version; saving a draft in place comes in 0.2.0 (PD-094).
- **No claim step on process tasks.** A candidate completes a task directly with `POST /tasks/{id}:complete`. `If-Match` and `Idempotency-Key` are required, so two candidates cannot overwrite each other, and four eyes is enforced on tasks marked `fourEyes`.
- **Decision history comes in 0.2.0.** Every decision is logged in `rle_decision`, but 0.1.0 has no API or cockpit screen to read the log. The Decisions area shows an empty state.
- **Display names show logins.** Versions and approvals show the identity recorded in the audit trail, for example `lan`, not a full name. Display names come in 0.2.0 from a host extension point.
- **No withdraw.** A requester cannot withdraw their own pending request in 0.1.0; an approver rejects it instead. Withdraw comes in 0.2.0.

### Breaking change coming in 0.2.0

The first change of 0.2.0 moves `Money`, the value types and the expression language into a new library, `bpm-expression` (ADR-0027). In 0.1.0 these types live under `io.github.dhluong90.bpm.rules`; in 0.2.0 they move to `io.github.dhluong90.bpm.expr`. Java code that imports them changes its imports. Rule set documents, REST payloads and stored data do not change.

### Upgrade notes

0.1.0 is the first release. These notes apply if you ran a build of `main` before it.

- **Rolling upgrade and lifecycle history (#152).** `V3` creates the history table and gives every existing version one `CREATED` row. While old replicas still run, they keep serving request-publish and approve but write no history rows, so those transitions are missing from `GET .../history` for good. If that matters, hold imports, requests and approvals until every replica runs 0.1.0. Evaluation is unaffected.
- **DMN extension namespace (#186).** Exports write `urn:horus-bpm:dmn:extensions:v1`. A file with the earlier spelling `urn:horus-bpm:dmn:extensions:1` is refused at import with its line and the replacement. Change the namespace in the file and import again.
- **Coordinates and packages.** The group id and Java packages are `io.github.dhluong90.bpm`. Builds of `main` before the rename used `com.horus.bpm`; change your dependencies and imports.
